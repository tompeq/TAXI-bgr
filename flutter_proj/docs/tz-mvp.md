# Такси Бгр: ТЗ на MVP и план развития

Версия: 0.3  
Дата обновления: 3 июля 2026 года

Документ написан для небольшой команды из двух человек: разработчика и юриста.
Это рабочее ТЗ, а не формальный договор. Спорные юридические и продуктовые
решения вынесены в конец документа.

## 1. Цель MVP

Сделать локальный сервис заказа такси и доставки для села Богородское
Ульчского района Хабаровского края.

На старте ожидается:

- 1-2 водителя;
- 5-7 водителей в течение первого месяца;
- около 20 заказов в день, возможное отклонение плюс-минус 7 заказов;
- Android-приложение первым;
- возможность позднее собрать iOS-версию без переписывания приложения;
- юридический статус диспетчерской на старте: самозанятый;
- название сервиса: «Такси Бгр».

### 1.1. Технологический стек

- мобильное приложение: Flutter, одна кодовая база для Android и будущей iOS;
- backend: NestJS;
- основная база данных: PostgreSQL с PostGIS;
- быстрые данные, блокировки и геопозиция: Redis;
- web-админка: React, TypeScript и Vite;
- карты, поиск и маршруты: Yandex MapKit Full;
- документы и фотографии: S3-совместимое объектное хранилище.

## 2. Роли системы

### 2.1. Пассажир

Может зарегистрироваться, выбрать адреса, создать заказ, наблюдать статус
заказа и положение назначенного автомобиля.

### 2.2. Водитель

Регистрируется с документами, получает доступ только после ручной проверки,
выходит на линию, видит доску заказов и принимает заказ по своему выбору.

### 2.3. Администратор

Работает через отдельную web-админку и имеет все административные права:
проверяет водителей и документы, видит заказы, пользователей, финансовую и
операционную статистику, выполняет блокировки, работает с чатом, тарифами,
опросами, диагностикой и служебными операциями.

Разделения административных полномочий на роли нет. Самостоятельной
регистрации администраторов нет, учётные записи создаются вручную.

## 3. Регистрация и доступ

### 3.1. Общий вход

Если пользователь ещё не зарегистрирован, показать выбор:

- «Я пассажир»;
- «Я водитель».

Телефон подтверждается по SMS.

### 3.2. Пассажир

Обязательные данные:

- номер телефона;
- имя.

Необязательные данные:

- фотография профиля.

### 3.3. Водитель

Обязательные данные:

- номер телефона;
- полное ФИО;
- фотография водительского удостоверения;
- фотография автомобиля с четырёх сторон.

После отправки анкета получает статус «На проверке». До ручного одобрения
водитель не может выйти на линию и принимать заказы.

Автоматическая проверка не входит в MVP. В будущем можно добавить:

- OCR водительского удостоверения;
- автоматическую сверку распознанного ФИО с анкетой;
- сравнение лица водителя с фотографией в удостоверении;
- liveness-проверку, подтверждающую присутствие живого человека.

Такой этап требует отдельной юридической проверки обработки биометрии и
персональных данных.

## 4. Пассажирское приложение

### 4.1. Карта и адреса

- Карта по умолчанию открывается на селе Богородское.
- Используется полная версия Yandex MapKit.
- Адрес можно ввести текстом или выбрать перемещением точки на карте.
- Поиск ограничивается рабочей территорией сервиса и не должен предлагать
  одноимённые адреса из других городов.
- Подсказки должны включать улицы, дома, организации и популярные объекты,
  например поликлинику, больницу, аэропорт или магазин.
- Первыми показываются совпадения из собственного справочника Богородского,
  Комбината, Гавани и Карьера. Поиск Yandex используется как дополнительный
  источник только в пределах рабочей области.
- Собственный справочник хранит название, тип объекта, координаты, тарифную
  зону, варианты написания и признак активности.
- Во время ввода показываются 2-3 часто используемых или последних адреса
  конкретного пассажира.
- После выбора подсказки карта плавно перемещается к найденному объекту.
- При ручном перемещении карты адрес обновляется обратным геокодированием.
- Поля «Откуда» и «Куда» не должны менять положение карты при появлении
  клавиатуры.
- В будущем можно добавить голосовой ввод адреса.

Адрес заказа всегда хранится в двух формах:

- текст для отображения;
- координаты latitude/longitude для карты, маршрута и определения зоны.

### 4.2. Создание заказа

Пассажир указывает:

- откуда ехать;
- куда ехать;
- тип: такси или доставка;
- количество пассажиров: 1, 2 или 3+;
- оплату: наличные или перевод;
- поездку сейчас или на выбранное время;
- поездку в одну сторону или туда-обратно.

Тариф «Попутчик» не входит в MVP.

### 4.3. Заказ на время

- Для обычного заказа тариф определяется по времени создания заказа.
- Для заказа на определённое время тариф определяется по времени поездки.
- Выбранное время можно удалить и вернуться к обычному заказу.

### 4.4. Туда-обратно

- Функцию можно включить при создании заказа.
- По согласованному требованию её также можно включить после принятия заказа.
- Стоимость обратной дороги равна стоимости дороги туда.
- Бесплатное ожидание: 10 минут.
- После 10 минут начисляется 10 рублей за каждую полную минуту.
- Неполная минута округляется в меньшую сторону.
- Таймер ожидания запускает водитель, подтверждение пассажира не требуется.

### 4.5. Статусы для пассажира

Минимальные статусы:

- заказ создан;
- заказ находится на доске;
- водитель назначен;
- водитель едет к пассажиру;
- водитель прибыл;
- поездка началась;
- ожидание;
- поездка завершена;
- заказ отменён.

После назначения водитель и автомобиль отображаются на карте.

Уведомления:

- заказ успешно создан;
- водитель принял заказ;
- водитель будет примерно через 3 минуты;
- водитель прибыл;
- заказ отменён;
- поездка завершена.

### 4.6. Поддержка

В MVP нужен чат пассажира с командой сервиса.

Рейтинги пассажиров и водителей в MVP не нужны.

## 5. Приложение водителя

### 5.1. Выход на линию

Основная кнопка: «Работать».

Только водитель, который вышел на линию:

- видит доску заказов;
- получает обычные push-уведомления о новых заказах;
- передаёт рабочую геопозицию.

### 5.2. Доска заказов

Все доступные заказы показываются общей доской.

В карточке заказа отображаются:

- откуда;
- куда;
- стоимость;
- количество пассажиров;
- способ оплаты;
- время поездки, если заказ предварительный;
- туда-обратно;
- тип заказа.

Цветовое различие:

- такси — красный акцент;
- доставка — зелёный акцент.

Водитель сам выбирает заказ. Один водитель может иметь только один активный
заказ.

### 5.3. Выравнивание дохода

Водители с доходом за последние 24 часа, заметно превышающим доход других
водителей, получают новые заказы с задержкой 20-30 секунд.

Доход для сравнения считается после вычета комиссии сервиса.

Все заказы остаются видимыми на доске после окончания персональной задержки.

### 5.4. Работа с принятым заказом

После принятия водитель получает:

- маршрут от текущего положения до пассажира;
- после начала поездки маршрут до точки назначения;
- данные пассажира и заказа;
- кнопки смены статуса;
- кнопку отмены с выбором причины.

Если после принятия водитель в течение 3 минут не меняет статус и не начинает
движение, заказ возвращается на доску.

### 5.5. Причины отмены водителем

- пассажир не вышел;
- пассажир не отвечает;
- пассажир ведёт себя неадекватно;
- число пассажиров не соответствует заявке;
- число пассажиров превышает количество посадочных мест;
- водитель сомневается в оплате, просит предоплату, пассажир отказывается.

### 5.6. Настройки и перерывы

- выбор принимаемых типов заказов: такси и доставка;
- фоновые уведомления о заказах: включить или выключить;
- вечерние и ночные уведомления: включить или выключить;
- перерыв на 10, 30 или 60 минут;
- закончить смену.

По последнему согласованному правилу уведомления о заказах получают только
водители, которые вышли на линию. Настройка вечерних и ночных уведомлений не
отменяет это ограничение.

## 6. Маршруты и геопозиция

### 6.1. Принятое решение для MVP

Дорожный граф не загружается и не хранится на нашем backend.

Маршруты строятся в мобильном приложении через Yandex MapKit Full:

- `DrivingRouter` получает начальную и конечную координаты;
- Yandex возвращает дорожную геометрию;
- приложение рисует маршрут на карте;
- из результата берутся расстояние и примерное время прибытия;
- при необходимости маршрут пересчитывается после отклонения водителя.

MapKit Full уже подключён к Flutter-проекту и официально поддерживает
автомобильную маршрутизацию.

Справка:

- https://yandex.com/maps-api/docs/mapkit/flutter/generated/tutorials/map_routing.html
- https://yandex.com/maps-api/docs/mapkit/flutter/generated/tutorials/map_routes.html

### 6.2. Что делает backend

Backend не рассчитывает геометрию маршрута в первой версии. Он:

- хранит координаты отправления и назначения;
- хранит текущий статус заказа;
- хранит последнюю геопозицию водителя;
- передаёт позицию водителя пассажиру через WebSocket;
- определяет тарифную зону;
- рассчитывает и фиксирует стоимость заказа по зоне, времени и надбавкам;
- фиксирует время прибытия, начала, ожидания и завершения;
- контролирует, какой пассажир имеет право видеть конкретного водителя.

Пассажирское и водительское приложения строят маршрут и получают ETA локально
через MapKit. При необходимости приложение может отправить информационную
оценку ETA на backend, но клиентское расстояние и ETA не участвуют в расчёте
стоимости и не считаются доверенными данными.

### 6.3. Передача позиции водителя

Во время активного заказа:

- приложение водителя получает GPS;
- отправляет координаты backend примерно каждые 3-5 секунд;
- backend хранит последнюю координату в Redis с коротким TTL;
- пассажир подписывается на обновления своего заказа по WebSocket;
- пассажирское приложение плавно перемещает маркер автомобиля между
  полученными координатами.

Маршрут не нужно запрашивать заново на каждую GPS-точку. ETA и дорожную линию
следует обновлять реже: при заметном отклонении от маршрута, смене статуса либо
примерно раз в 20-30 секунд во время движения.

Когда водитель просто находится на линии без активного заказа, допустим
более редкий интервал, например 10-15 секунд.

Для истории и разбора споров не обязательно сохранять каждую точку. Можно
сохранять прореженный трек раз в 15-30 секунд и важные точки смены статуса.

### 6.4. Какие маршруты нужны

1. Водитель → пассажир.
2. Пассажир → точка назначения.
3. Обратный маршрут для заказа туда-обратно.
4. В будущем — маршруты попутчика и предложения обратных заказов.

### 6.5. Что сделать сейчас

До backend нужно сделать небольшой маршрутный прототип во Flutter:

- построить маршрут между выбранными «Откуда» и «Куда»;
- нарисовать реальную дорожную полилинию;
- показать расстояние и ETA;
- проверить несколько маршрутов по Богородскому, Комбинату, Гавани и Карьеру;
- проверить, что Yandex знает местные дороги и не строит невозможные проезды.

После проверки дорожного графа основная разработка должна перейти к backend.
Полноценное отображение движения водителя без backend делать рано, потому что
источника реальных координат другого пользователя пока нет.

### 6.6. Возможное развитие

Если в будущем backend должен самостоятельно получать маршрут, ETA или
использовать их при автоматическом распределении заказов, потребуется
отдельный серверный Routing API и отдельная проверка лицензии/тарифа.
Мобильный ключ MapKit нельзя считать готовым серверным ключом.

### 7.1. Дневной тариф

- Верхний БГР: 200 рублей.
- Комбинат: 250 рублей.
- Нижняя Гавань: 700 рублей.
- Карьер под Гаванью: 500 рублей.

Цена определяется фиксированными зонами на карте, а не длиной маршрута.

### 7.2. Вечерний тариф, 19:00-21:00

- Верхний БГР: 300 рублей.
- Комбинат: 350 рублей.
- Нижняя Гавань: 900 рублей.
- Карьер: 650 рублей.

### 7.3. Ночной тариф, 21:00-06:00

- Верхний БГР: 400 рублей.
- Комбинат: 500 рублей.
- Нижняя Гавань: 1500 рублей.
- Карьер: 1000 рублей.

Тариф меняется автоматически.

### 7.4. Надбавка за состояние дороги

Надбавка за плохое дорожное покрытие составляет 20%.

По согласованному правилу дорожная надбавка не складывается с вечерним или
ночным тарифом и применяется только к дневному тарифу.

Пассажир видит предупреждение о временном повышении стоимости.

Точная логика голосований и снятия надбавки требует окончательного
подтверждения заказчика.

## 8. Отмена заказа пассажиром

Согласованная основа:

- первые 3 минуты после создания — бесплатно;
- далее возможен штраф 50 рублей;
- при более поздней отмене — 100 рублей;
- после 10 минут — полная стоимость заказа.

Точные границы интервалов сейчас сформулированы неоднозначно и должны быть
зафиксированы заказчиком до реализации списания.

## 9. Нет доступных водителей

- Если водителей нет днём, сразу сообщить об отсутствии машин.
- Если водителей нет ночью, предложить пассажиру подождать до 10 минут.
- Ночной заказ отправить водителям, которые находятся на линии и включили
  соответствующие уведомления.
- Если заказ никто не принял, сообщить, что водителей нет.

## 10. Комиссия и деньги

### 10.1. Тестовый период

Первый месяц MVP комиссия не взимается.

После тестового периода планируется комиссия 10%. Возможное увеличение до
15% является будущим решением.

Комиссия начисляется с выполненных заказов такси и доставки. После появления
тарифа «Попутчик» он также включается в комиссионную схему.

### 10.2. Наличные

Пассажир передаёт полную сумму водителю.

Система начисляет водителю долг перед сервисом на сумму комиссии.

Погашение:

- водитель переводит деньги сервису;
- администратор вручную подтверждает получение;
- подтверждённая сумма уменьшает долг.

Уровни долга:

- до 1000 рублей — сумма видна при входе;
- 1000-3000 рублей — напоминание в чате;
- 5000 рублей — созвон и возможность блокировки.

Временная блокировка выполняется из админки. Причина вводится свободным
текстом.

### 10.3. Безналичная оплата

В MVP допускается перевод по согласованному простому сценарию.

«Правильный безнал» является отдельным этапом:

- оплата пассажиром через платёжного провайдера или СБП;
- автоматическое удержание комиссии;
- перечисление остатка водителю;
- чеки и возвраты;
- привязка платежа к заказу;
- обработка частичного и полного возврата;
- юридически корректная роль сервиса и водителя.

Идея оплаты QR-кодом через сайт требует проверки юристом и платёжным
провайдером. Нельзя считать, что обычный QR автоматически решает удержание
комиссии, чеки и выплаты физлицам.

## 11. Админ-панель

### 11.1. Водители

- список заявок на регистрацию;
- просмотр ФИО, телефона, прав и фотографий автомобиля;
- одобрение или отказ;
- временная блокировка;
- свободное текстовое поле причины блокировки;
- просмотр заказов, дохода, комиссии и долга;
- ручное подтверждение погашения долга.

### 11.2. Заказы

- список всех заказов;
- фильтры по датам, статусам, типам, водителям и пассажирам;
- карточка заказа со всеми временными отметками;
- причины отмены;
- история смены статусов;
- способ оплаты;
- полная цена, комиссия и доход водителя.

Администратор видит все заказы и все данные, необходимые для проверки спорных
ситуаций.

### 11.3. Чат

- диалоги с пассажирами;
- диалоги с водителями;
- системные напоминания о комиссии;
- сохранение истории сообщений.

### 11.4. Пассажиры

- список зарегистрированных пассажиров;
- имя, телефон, дата регистрации и последнее время активности;
- история заказов пассажира;
- история обращений в поддержку.

### 11.5. Тарифы, зоны и адресный справочник

Администратор может:

- просматривать и изменять дневные, вечерние и ночные тарифы;
- редактировать границы фиксированных тарифных зон на карте;
- добавлять, изменять и отключать улицы, дома и организации;
- задавать координаты и варианты написания локального адреса;
- добавлять популярные точки, которые показываются в поиске;
- просматривать историю изменений тарифов и зон.

Изменение тарифа или зоны не должно менять стоимость уже созданного заказа.

### 11.6. Качество дорог

- результаты голосований по каждой зоне;
- список проголосовавших водителей и время ответа;
- история включения и выключения надбавки;
- ручное включение и снятие надбавки администратором;
- текст предупреждения, которое увидит пассажир.

## 12. Аналитика в админ-панели

Добавить отдельный раздел «Статистика».

Фильтры периода:

- день;
- неделя;
- месяц;
- год;
- произвольный диапазон.

### 12.1. Входы и выходы

Показывать:

- количество успешных входов;
- количество явных выходов из аккаунта;
- количество уникальных вошедших пользователей;
- разбивку по пассажирам, водителям и администраторам;
- последнее время активности пользователя.

Закрытие приложения или истечение сессии не следует считать явным выходом.
Для этого нужны отдельные события.

### 12.2. Заказы

Показывать:

- зарегистрированные (созданные) заказы;
- выполненные заказы;
- разницу между созданными и выполненными;
- процент выполнения;
- отменённые пассажиром;
- отменённые водителем;
- не принятые ни одним водителем;
- возвращённые на доску;
- разбивку на такси и доставку;
- разбивку по наличным и безналичным.

Формула:

`Разница = созданные заказы - выполненные заказы`.

Разница должна раскрываться по причинам, чтобы было видно, куда пропали
невыполненные заказы.

### 12.3. Доход каждого водителя

В интерфейсе заказчик называет показатель «ЗП», но технически это доход
водителя от выполненных заказов.

Для каждого водителя показывать за день, неделю, месяц, год и произвольный
период:

- количество выполненных заказов;
- полную стоимость выполненных заказов;
- оплату наличными;
- оплату переводом/безналичными;
- начисленную комиссию;
- чистый доход после комиссии;
- текущий долг по наличной комиссии;
- подтверждённые погашения долга;
- средний доход на заказ.

Базовая формула:

`Чистый доход = сумма выполненных заказов - комиссия сервиса`.

До юридического решения отдельно не включать в чистый доход штрафы за отмену
и платное ожидание. Их распределение между водителем и сервисом нужно
зафиксировать.

### 12.4. Экспорт

Желательно предусмотреть экспорт таблиц в CSV/XLSX за выбранный период.
Для первой версии допустим CSV.

## 13. Опрос водителей по ценам

Раз в 3 дня каждому одобренному водителю показывается опрос:

«Устраивают ли вас текущие цены на поездки?»

Варианты:

- устраивают;
- не устраивают.

Дополнительно показывается поле:

«Какую цену или изменение вы предлагаете?»

Правила:

- при ответе «не устраивают» предложение обязательно;
- при ответе «устраивают» комментарий необязателен;
- опрос не должен блокировать выход на линию;
- если водитель закрыл опрос, он остаётся доступным до ответа;
- один водитель может отправить только один ответ за один период;
- вместе с ответом сохраняется снимок действовавших тарифов;
- следующий опрос создаётся через 3 дня после начала предыдущего периода.

В админ-панели показывать:

- сколько водителей ответило;
- сколько устраивает;
- сколько не устраивает;
- процент каждого ответа;
- список текстовых предложений;
- историю результатов по периодам;
- фильтр по водителю.

Опрос по ценам не изменяет тариф автоматически. Решение принимает команда
сервиса вручную.

## 14. Опрос о состоянии дорог

Требование сохраняется, но относится к этапу после основной механики заказов.

- Отдельная оценка дорог по БГР не чаще одного раза в день для каждого
  водителя.
- Отдельная оценка дороги в Гавань.
- Шкала от 0 до 10.
- Опрос по дороге в Гавань после поездки туда.
- Предварительный порог для БГР: 3 негативных ответа и 0 нормальных.
- Предварительный порог для дороги в Гавань: 2 негативных ответа и 0
  нормальных.
- Учитываются ответы уникальных водителей и время каждого голосования.
- При достижении согласованного порога возможна дневная надбавка 20%.
- Надбавка снимается после достаточного количества хороших оценок.
- Администратор может вручную включить или снять надбавку.

Порог, срок действия голосов и определение «хорошей» оценки нужно окончательно
зафиксировать до реализации.

## 16. События для статистики

Статистику нельзя надёжно восстанавливать только из текущего состояния
таблиц. Backend должен сохранять события:

- `user_registered`;
- `login_succeeded`;
- `logout`;
- `driver_went_online`;
- `driver_went_offline`;
- `order_created`;
- `order_accepted`;
- `order_returned_to_board`;
- `order_started`;
- `order_completed`;
- `order_canceled`;
- `commission_accrued`;
- `commission_payment_confirmed`;
- `price_survey_created`;
- `price_survey_answered`.

Для каждого события хранить:

- время;
- пользователя;
- роль;
- заказ или водителя, если применимо;
- технические метаданные;
- источник события.
